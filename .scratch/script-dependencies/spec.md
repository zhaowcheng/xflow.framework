# Scripts 项目脚本接口规格

Status: ready-for-agent

## Problem Statement

项目目前通过 `Node.exec_script` 传入脚本路径和原始参数字符串，并在独立的 `deps.json` 中维护脚本依赖声明。脚本的调用方式、参数约定和依赖关系分散，Pipeline 的调用者需要直接了解具体脚本路径及参数拼接方式；Node 同时承担节点基础操作和项目脚本执行流程。

项目开发者希望用自己定义的方法表达脚本入口，将参数处理和脚本依赖声明集中在项目的 Scripts 中。Pipeline 应自动获得当前项目的 Scripts 实例，调用者通过具名的脚本入口完成工作，同时保留现有的依赖上传、执行目录、环境变量、执行结果和错误传播规则。

## Solution

框架提供通用的 `Scripts` 基类。每个项目必须在 `scripts/__init__.py` 中定义继承该基类、类名同为 `Scripts` 的项目类，在类属性 `DEPS` 中维护脚本依赖声明，并按需定义普通方法作为脚本入口。脚本入口的名称和参数由项目决定；入口内部调用继承的 `__exec`，明确给出目标脚本相对脚本根目录的路径、原始参数字符串和可选环境变量。

Pipeline 在实例化时自动加载当前项目的 Scripts，并使用自己的节点建立 `self.scripts`。初始化只绑定节点；依赖检查、上传和执行在实际调用脚本入口时发生。即使项目没有脚本，也必须提供空的项目 Scripts 类。新项目模板直接生成这一结构。

框架负责递归解析声明的依赖、完成上传前检查、保留相对目录结构并执行目标脚本。Node 继续提供上传、执行命令和目录上下文等基础能力。本次一次性移除 `Node.exec_script` 和 `deps.json` 机制，项目迁移到新的脚本入口，不设置兼容期。

## User Stories

1. 作为项目开发者，我希望继承框架提供的 Scripts 基类，以便复用依赖解析、上传和执行能力。
2. 作为项目开发者，我希望将脚本依赖声明和脚本入口集中在项目 Scripts 中，以便在同一处维护脚本的使用约定。
3. 作为项目开发者，我希望通过 `DEPS` 字典声明脚本的直接依赖，以便明确表达项目实际需要交付的脚本关系。
4. 作为项目开发者，我希望没有声明条目的脚本按无声明依赖处理，以便无需为每个独立脚本维护空列表。
5. 作为项目开发者，我希望自由命名脚本入口，以便用项目业务含义表达操作，而不必沿用脚本文件名。
6. 作为项目开发者，我希望脚本入口使用普通方法并自行声明参数，以便由入口集中处理参数约定。
7. 作为项目开发者，我希望在入口内明确选择目标脚本，以便入口名称和实际脚本保持独立。
8. 作为项目开发者，我希望仅作为依赖使用的脚本不必定义独立入口，以便保持项目接口简洁。
9. 作为项目开发者，我希望入口自己组装原始参数字符串并处理 Shell 引号，以便保留现有 Shell 参数语义。
10. 作为 Pipeline 编写者，我希望实例化 Pipeline 后即可使用 `self.scripts`，以便无需手动选择、加载或实例化项目 Scripts。
11. 作为 Pipeline 编写者，我希望通过具体的脚本入口调用脚本，以便不在 Pipeline 中重复维护脚本路径和参数拼接逻辑。
12. 作为 Pipeline 编写者，我希望无需增加项目 Pipeline 的类型注解或配置，以便直接使用自动加载机制。
13. 作为项目开发者，我希望 Scripts 绑定当前 Pipeline 的节点，以便脚本操作使用本次流水线选定的执行节点。
14. 作为项目开发者，我希望 Scripts 初始化时不访问尚未就绪的远端工作目录，以便与 Pipeline 后续 setup 的生命周期一致。
15. 作为项目开发者，我希望仅在实际调用入口时检查依赖和交付脚本，以便初始化不会提前解析声明、上传文件或执行命令。
16. 作为多个项目的维护者，我希望每个 Pipeline 加载自己项目的 Scripts，以便相同的包名不会导致串用另一个项目的脚本入口。
17. 作为项目开发者，我希望相对项目路径在本地工作目录变化后仍指向原项目，以便脚本来源不随运行环境意外改变。
18. 作为项目开发者，我希望缺少项目 Scripts 文件或类时在 Pipeline 初始化阶段明确失败，以便及时发现项目结构不完整。
19. 作为项目开发者，我希望类的构造契约错误、模块导入错误和语法错误明确暴露，以便能定位真实原因，而不是得到空脚本集合。
20. 作为无脚本项目的维护者，我希望可以提供 `DEPS` 为空且没有脚本入口的项目 Scripts 类，以便遵守统一的项目结构。
21. 作为新项目开发者，我希望初始化命令生成可加载的空项目 Scripts 类，以便从新接口开始开发。
22. 作为项目开发者，我希望框架只接受相对脚本根目录且未越界的脚本路径，以便上传范围明确。
23. 作为项目开发者，我希望绝对路径、越界路径和指向根目录外的符号链接被拒绝，以便不会交付脚本根目录以外的内容。
24. 作为项目开发者，我希望脚本路径经过一致的归一化，以便入口和依赖声明可以正确匹配并去重。
25. 作为项目开发者，我希望框架递归收集直接和间接依赖，以便只声明直接关系即可完成本次脚本交付。
26. 作为项目开发者，我希望重复依赖和多个分支共享的依赖只上传一次，以便避免重复交付。
27. 作为项目开发者，我希望目标脚本和依赖脚本保留相对子目录，以便脚本可以沿用原有的相对引用方式。
28. 作为项目开发者，我希望声明格式和路径错误在任何脚本上传之前被发现，以便不因可预先发现的配置错误产生部分上传。
29. 作为项目开发者，我希望本次需要的文件缺失或存在循环依赖时在上传前失败，以便不会执行不完整的脚本集合。
30. 作为项目开发者，我希望错误能指出相关脚本或循环关系，以便直接修正声明。
31. 作为项目开发者，我希望格式和路径合法但与本次目标无关的缺失文件或循环不阻止执行，以便独立脚本之间不产生额外限制。
32. 作为项目开发者，我希望框架只执行目标脚本，以便由脚本自身决定如何引用或调用依赖脚本。
33. 作为 Pipeline 编写者，我希望目标脚本在当次 `Node.scriptdir` 中执行，以便执行目录与当前节点目录上下文一致。
34. 作为 Pipeline 编写者，我希望执行完成或失败后恢复外层目录上下文，以便后续命令继续在预期目录中运行。
35. 作为项目开发者，我希望远端目标脚本已存在时直接复用，以便无需重新检查本地依赖、补传或自动刷新文件。
36. 作为项目开发者，我希望远端目标不存在时上传完整的本次依赖集合，以便不依赖远端依赖文件是否已经存在。
37. 作为项目开发者，我希望执行结果继续返回 `CommandResult`，以便脚本入口可以向调用者返回既有结果类型。
38. 作为项目开发者，我希望可选环境变量、nixenv 包装和非零返回码的 `CommandError` 继续生效，以便现有执行语义保持一致。
39. 作为多个 Pipeline 的维护者，我希望框架不会原地修改类级 `DEPS`，以便一个实例执行脚本不会改变其他实例的依赖声明。
40. 作为项目开发者，我希望项目初始化模板的 README.md 包含脚本编写指南，说明入口定义、固定类名约定和依赖声明，以便在生成的项目中直接了解如何编写和调用脚本。
41. 作为框架维护者，我希望脚本流程由 Scripts 承担、Node 保留基础操作，以便职责划分与项目脚本接口一致。
42. 作为框架维护者，我希望新模板和脚本编写指南只提供当前 Scripts 接口的使用方式，以便后续项目统一使用新方案。

## Implementation Decisions

1. **职责划分。** 在框架的 `xflow.framework.scripts` 模块提供原名为 `Scripts` 的基类，承接依赖声明校验、依赖收集、脚本交付和执行流程。项目 Scripts 提供 `DEPS` 与具名脚本入口；Node 提供上传文件、执行命令、存在性检查和目录上下文等基础能力。Pipeline 负责加载和实例化项目 Scripts。
2. **项目类契约。** 框架基类与项目子类在类定义中都固定名为 `Scripts`，项目子类必须继承框架基类。导入时可以为基类使用别名。构造器必选参数为 `node: Node`；项目脚本入口不得覆盖构造器、`__exec` 等框架必需成员。不支持任意名称的项目子类，也不增加另一套注册或注入配置。
3. **统一执行方法。** `__exec` 接受必选的 `script: str | Path`、默认值为空字符串的 `argstr: str` 和默认值为 `None` 的 `envs: Optional[Dict[str, str]]`，返回 `CommandResult`。项目脚本入口通过 `self.__exec` 调用继承实现。双下划线会依据类定义名改写为 `_Scripts__exec`，因此固定类名是接口约束；这表示内部使用约定，不承诺阻止所有外部访问。
4. **入口与参数。** 脚本入口是普通方法，名称不必与目标脚本同名，参数由项目定义。入口明确传入目标脚本的相对路径，自行组装原始参数字符串并负责必要的 Shell 引号；框架不引入参数列表、自动参数映射或改变参数字符串的 Shell 解释语义。Pipeline 按约定调用具体入口，不另设接受任意脚本路径的公开执行入口。依赖脚本无需独立入口。
5. **自动加载。** Pipeline 构造时按自身项目目录定位项目脚本包，加载其中的项目 Scripts，并用当前节点建立 `self.scripts`。所有项目都必须满足这一结构，包括无脚本项目。加载必须隔离同一进程中不同项目的同名脚本包，不能因模块缓存、搜索路径或本地工作目录变化串用其他项目的类。具体加载机制留给实现选择，不扩展为通用模块加载框架。
6. **初始化失败。** 项目脚本包入口文件缺失、Scripts 类缺失或不符合基类及构造契约、模块内部导入失败或语法错误，均在 Pipeline 初始化阶段明确暴露，保留可定位的错误原因；不得静默回退为空 Scripts。类级依赖声明是否有效不在此阶段检查。
7. **生命周期。** Scripts 构造器只绑定节点状态，不缓存尚未就绪的远端目录，不提前解析、归一化或验证 `DEPS`，也不上传或执行脚本。实际调用脚本入口时，统一执行方法读取当前节点的目录上下文。只保证在 Pipeline 中使用。
8. **声明结构。** `DEPS` 是只读的类级字典：键为脚本相对脚本根目录的路径字符串，值为其直接依赖脚本的相对路径字符串列表。空字典表示无声明依赖；没有条目的脚本按无声明依赖处理。框架校验、归一化和遍历时不得原地修改字典或其中的列表，也不从脚本文本推断依赖。
9. **路径规则。** 目标脚本接受字符串或 Path，声明中的路径使用字符串；全部按项目脚本根目录解释并归一化。拒绝绝对路径、归一化后指向根目录自身或根目录外的路径，以及解析后逃逸根目录的符号链接。合法的根目录内部符号链接沿用现有文件交付语义。目标路径范围检查不因远端目标已存在而取消。
10. **上传前检查。** 远端目标不存在时，先检查整份 `DEPS` 的结构与路径，再收集目标可达的依赖并检查循环，最后检查本次目标及依赖对应的本地文件。所有这些检查成功后才开始交付。声明中与目标无关的条目仍须满足结构和路径规则，但其缺失文件或不可达循环不阻止本次调用。路径、声明或可达循环错误沿用 `ValueError`，本次所需文件缺失沿用 `FileNotFoundError`；错误说明相关条目或路径，循环错误说明循环关系。
11. **依赖交付。** 递归收集直接与间接依赖，按归一化后的相对路径去重。目标与依赖保留相对子目录并交付到本次节点脚本目录，沿用目标脚本的可执行权限处理。目标不存在时上传整个集合，不逐个检查远端依赖是否存在。不将上传顺序作为公开接口，也不依次执行依赖脚本。
12. **远端复用。** 远端目标已存在时直接执行，不读取或验证 `DEPS`，不要求本地目标及依赖文件存在，不补传依赖、不重设权限、不自动刷新远端文件。只保留调用目标路径本身应有的范围校验。
13. **执行语义。** 目标脚本在当次 `Node.scriptdir` 中执行；沿用 Node 的执行能力、nixenv 包装、可选环境变量及现有解释器约定。原始参数字符串保持现有解释语义，执行结果返回 `CommandResult`，非零返回码继续抛出 `CommandError`。正常或异常退出均恢复进入脚本执行前的目录，普通 Node 命令仍使用 `Node.cwd`。
14. **一次切换。** 移除旧的 Node 脚本执行入口与 JSON 依赖声明机制，不提供双入口、回退读取、兼容模式或过渡期。新项目模板生成继承框架基类、`DEPS` 为 `{}` 且没有示例依赖或脚本入口的项目 Scripts 类。同步更新项目初始化模板和相关测试夹具，并在模板目录的 README.md 中增加脚本编写指南，说明入口定义、依赖声明、Shell 参数责任、固定类名和 Pipeline 调用方式；不编写迁移指南，不增加用于编辑器补全的项目 Pipeline 类型注解或额外配置。

## Testing Decisions

1. **主要测试边界：Pipeline 加载并调用项目脚本入口。** 在临时项目中定义真实的项目 Scripts 和最小 Pipeline，由 Pipeline 初始化自动加载 Scripts，再在 Pipeline 阶段中调用具名入口。复用现有 `FakeConnection`，观察上传文件的路径与内容、实际目标命令、环境变量、执行目录、返回值和异常。依赖处理与执行的大部分验收都集中在这一条调用链，不直接测试私有解析函数或名字改写后的方法。
2. **初始化行为。** 通过 Pipeline 构造验证必需的项目结构、正确绑定当前节点以及文件、类、继承或构造契约、模块导入和语法错误。无脚本项目可以初始化；合法 Python 模块中的无效 `DEPS` 不应提前验证，只有实际调用入口且远端目标不存在时才校验。模块语法或导入错误始终在初始化时暴露，不能因远端目标存在而跳过。Scripts 构造发生在 buildid 与远端工作目录就绪之前，其加载和初始化不应触发脚本相关的远端存在性检查、上传或执行。
3. **加载隔离与实际调用。** 在同一进程先后加载具有不同入口行为的两个临时项目，并验证再次使用原实例仍调用正确项目的类。项目切换之间不手动清空脚本包的模块缓存，以免掩盖串用问题。覆盖相对项目路径、本地目录变化以及固定类名下入口调用继承 `__exec` 的真实行为；不约束加载器内部缓存名或使用哪种导入 API。
4. **依赖与路径。** 经由项目入口覆盖空声明、未声明目标、直接依赖、多层依赖、共享与重复依赖、路径归一化、相对子目录、合法内部符号链接、路径越界和符号链接逃逸。覆盖整份声明的格式及路径错误、目标和可达依赖缺失、直接及间接循环，并验证上传前失败。验证无关缺失文件及不可达循环不会阻断合法目标，且执行前后 `DEPS` 及其列表内容保持不变。
5. **远端分支。** 目标已存在时，用无效声明和缺失本地脚本证明本地依赖检查被跳过，且没有上传、补传、权限重设或刷新。目标不存在时，即使某个依赖已在远端存在，也上传完整去重集合。覆盖首次交付后再次调用的复用行为，并验证只执行目标脚本。
6. **执行约定。** 覆盖由入口拼接并包含必要引号的原始参数字符串、可选环境变量、nixenv、`CommandResult` 和 `CommandError`。在不同节点目录上下文中调用同一 Scripts 实例，验证每次读取当次 `Node.scriptdir`，正常及异常退出均恢复外层目录。直接调用阶段或项目入口时断言原异常传播；经 `Pipeline.run()` 调用时按既有生命周期断言 `FAILED` 结果，不要求改变 Pipeline 的异常处理。保留普通 Node 命令及连接目录上下文的既有回归测试。
7. **辅助测试边界：CLI 项目初始化。** 复用 `CliRunner` 和临时目录，通过实际初始化命令验证模板产物。生成的项目包含可由 Pipeline 加载的空 Scripts 类，不含旧依赖声明文件，不预置示例依赖或脚本入口；生成项目的 README.md 包含正确展示当前 Scripts 接口的脚本编写指南。由新模板构造 Pipeline，验证模板与自动加载契约一致。
8. **复用已有测试先例。** 现有 Node 测试已使用 `FakeConnection` 记录上传、远端存在性和执行信息，并覆盖依赖闭包、路径、目录恢复及错误传播；将相关行为迁移到新的公开调用链。现有 Pipeline 测试使用临时项目和 `FakeEnv` 验证生命周期；现有 CLI 测试使用 `CliRunner` 验证初始化和运行。这些夹具应补齐必需的空项目 Scripts，不为旧接口保留兼容分支。
9. **测试质量和验证范围。** 断言调用者可观察的行为，不断言私有方法调用、内部遍历算法、上传顺序或命令列表的固定索引。按目标命令和实际交付内容定位断言。实现完成后运行受影响的 Scripts、Pipeline、CLI、Node 和连接回归测试，并检查安装包包含新框架模块及初始化模板。连接替身测试不能表述为真实 SSH 或 Docker 集成验证。本次规格整理不代表功能已实现或测试已通过。

## Out of Scope

- 保留 `Node.exec_script`、读取或生成 `deps.json`，以及兼容期、双机制运行或自动迁移工具。
- 从 Shell 内容推断依赖，新增 Shell 解析器，或自动发现脚本入口。
- 参数列表 API、自动参数映射、自动代替项目入口处理参数字符串的 Shell 引号。
- 任意名称的项目 Scripts 子类、自动生成入口、通用插件注册系统或可配置的 Scripts 类选择机制。
- 支持 Pipeline 之外独立使用 Scripts，或在 Scripts 初始化时交付脚本。
- 额外的 Pipeline 类型注解、编辑器补全配置或类型生成工具。
- 旧项目迁移指南或独立的迁移文档。
- 远端脚本内容同步、依赖逐项缓存判断、增量刷新、上传失败回滚或多调用并发协调。
- 调度或逐一执行依赖脚本，改变脚本解释器约定，或者重构无关的 Node、SSH、Docker 和 Pipeline 功能。
