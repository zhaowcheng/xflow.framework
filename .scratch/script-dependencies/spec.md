# 脚本依赖解析

Status: ready-for-agent

## Problem Statement

脚本编写者把公共逻辑提取为依赖脚本后，框架仍只上传目标脚本，远端执行时可能找不到它引用的文件。现有上传还会丢弃本地子目录结构，脚本执行工作目录与脚本存放目录不同，导致调用者难以采用统一的引用路径。

目前，调用者必须自行维护依赖上传和路径处理。这些重复工作应由框架承担，使脚本编写者只需要维护脚本依赖声明，就能在节点上执行目标脚本及其依赖。

## Solution

由脚本编写者在脚本根目录维护 `deps.json`，显式声明各脚本的直接依赖。框架在远端目标脚本不存在时，递归收集本次需要的依赖脚本，完成检查后一次上传所需文件，并保留相对目录结构。

`Node.exec_script` 的脚本参数、脚本依赖声明和脚本之间的引用统一使用相对脚本根目录的路径；脚本执行工作目录统一为当次调用的 `Node.scriptdir`。远端目标脚本已存在时，继续复用该脚本，不检查或补传依赖。

新项目提供空的脚本依赖声明及使用说明。旧项目没有声明文件时视为没有声明依赖，但现有调用和脚本中的相对路径需要按新的目录约定迁移。

## User Stories

1. 作为脚本编写者，我希望在脚本根目录维护一份脚本依赖声明，以便集中说明哪些公共脚本需要随目标脚本上传。
2. 作为脚本编写者，我希望显式声明依赖而不依赖框架分析脚本内容，以便准确控制需要交付的文件。
3. 作为框架调用者，我希望用相对脚本根目录的路径指定目标脚本，以便入口参数与依赖声明使用同一套路径约定。
4. 作为框架调用者，我希望直接执行脚本根目录中的目标脚本，以便常见单脚本调用保持简单。
5. 作为框架调用者，我希望执行子目录中的目标脚本，以便按用途组织项目脚本。
6. 作为脚本编写者，我希望框架上传目标脚本的直接依赖，以便目标脚本可以引用公共脚本。
7. 作为脚本编写者，我希望框架递归收集间接依赖，以便依赖脚本也能引用其他公共脚本。
8. 作为脚本编写者，我希望本次上传集合中的共享依赖只处理一次，以便多个引用不会导致重复上传。
9. 作为脚本编写者，我希望依赖上传后保留相对目录结构，以便远端引用路径与本地约定一致。
10. 作为脚本编写者，我希望不同子目录中的同名脚本保持各自位置，以便它们不会因为只保留文件名而相互覆盖。
11. 作为框架调用者，我希望远端目标脚本不存在时上传完整依赖集合，以便首次执行具备本次声明所需的文件。
12. 作为框架调用者，我希望远端目标脚本存在时直接执行，以便继续保留现有复用行为。
13. 作为框架调用者，我希望复用远端目标脚本时跳过本地依赖检查及补传，以便复用行为不额外依赖本地声明或依赖文件是否完备。
14. 作为旧项目维护者，我希望缺少声明文件时按空声明处理，以便没有依赖的项目不必先添加配置文件。
15. 作为脚本编写者，我希望没有声明条目的目标脚本按无依赖处理，以便只为有依赖的脚本维护条目。
16. 作为脚本编写者，我希望声明格式错误时在上传前得到明确错误，以便修正配置后再执行。
17. 作为脚本编写者，我希望本次需要的目标脚本或依赖脚本缺失时在上传前报错，以便避免上传不完整的文件集合。
18. 作为脚本编写者，我希望循环依赖在上传前报错并显示循环路径，以便直接找到需要修改的声明。
19. 作为项目维护者，我希望入口参数及声明中的路径限定在脚本根目录内，以便项目脚本不会意外引用目录外的文件。
20. 作为项目维护者，我希望绝对路径及越出脚本根目录的路径被拒绝，以便调用者遵守统一的定位规则。
21. 作为脚本编写者，我希望目标脚本在远端脚本根目录中执行，以便脚本之间统一使用相对脚本根目录的引用路径。
22. 作为框架调用者，我希望脚本参数和环境变量继续按现有接口传入，以便现有参数及环境配置可以继续使用。
23. 作为框架调用者，我希望脚本执行继续使用现有 `nixenv` 包装，以便声明的运行环境仍然生效。
24. 作为框架调用者，我希望普通 `Node.exec` 继续在 `Node.cwd` 中执行，以便普通命令的工作目录不因脚本功能变化而改变。
25. 作为框架调用者，我希望 `node.dir(...)` 仍同时影响当次远端工作目录和脚本目录，以便继续采用现有节点目录管理方式。
26. 作为 SSH 或 Docker 节点使用者，我希望通过同一 Node 接口得到相同的依赖上传行为，以便不必分别维护脚本交付逻辑。
27. 作为新项目创建者，我希望初始化项目时自动获得内容为 `{}` 的声明文件，以便直接开始维护脚本依赖。
28. 作为新项目创建者，我希望模板说明依赖声明由脚本编写者维护，以及入口、声明和引用路径的约定，以便正确编写第一次脚本调用。
29. 作为旧项目维护者，我希望明确知道调用中的 `scripts/` 前缀需要移除，以便迁移到相对脚本根目录的入口参数。
30. 作为旧项目维护者，我希望了解执行目录变化对相对输入、参数和输出位置的影响，以便迁移脚本时调整这些路径。
31. 作为框架维护者，我希望测试通过公开调用观察上传、执行和错误行为，以便内部实现变化时仍能验证用户约定。

## Implementation Decisions

- 依赖处理放在框架的 Node 脚本执行功能中；不在业务项目中分别实现，也不解析 shell 内容来推断依赖。
- 本地脚本根目录取当前 Pipeline 的项目目录下的 `scripts` 目录，不随本地进程工作目录或远端 `node.dir(...)` 改变。本次不新增脚本根目录配置接口。
- 保留 `Node.exec_script(script, argstr, envs)` 的接口形状与返回结果约定。`script` 统一为相对脚本根目录的路径；绝对路径及越出根目录的路径直接报错，不增加项目外脚本的特殊处理分支。
- 同一相对路径用于本地源文件定位、脚本依赖声明匹配及远端文件定位。子目录中的脚本保留其完整相对路径，不再只使用文件名。
- 脚本依赖声明使用 `deps.json`。缺少该文件时等价于空字典；声明必须是字典，键为脚本相对路径，值为依赖脚本相对路径组成的列表。没有对应条目表示没有声明依赖。
- 声明中的键及列表元素必须是脚本根目录内的相对路径，禁止绝对路径和通过 `..` 越出根目录的路径。
- 入口参数通过路径范围检查后，先判断远端目标脚本是否存在。存在时直接执行，不读取依赖声明，不检查本地依赖文件是否存在，也不补传依赖。
- 远端目标脚本不存在时，读取声明，递归收集目标脚本的直接和间接依赖，按文件路径去重；同一次调用中，每个文件只上传一次。
- 上传前完成声明格式、路径范围、本次所需文件及循环依赖检查。声明的结构和路径必须合法；文件存在性与循环检查针对本次目标脚本可达的依赖集合，不要求上传无关脚本。
- 检查失败时明确报错，不上传任何文件，也不执行目标脚本。循环依赖的错误包含循环路径；文件缺失的错误指出所缺文件。此处保证的是检查失败不产生上传或目标执行，不承诺网络传输失败后的远端回滚。
- 检查通过后，按需创建远端父目录，上传目标脚本及全部依赖脚本，保留脚本根目录内的相对结构，并保留目标脚本上传后的执行权限设置。
- 本次不增加逐个依赖脚本的远端存在判断、内容比较或更新判断。远端目标脚本不存在时，即使某个依赖已在远端存在，仍按本次完整上传集合处理。
- `Node.exec_script` 的执行工作目录改为当次调用的 `Node.scriptdir`，保留参数、环境变量、现有 `nixenv` 包装和命令结果／错误传播约定。实现不能通过调用普通 `Node.exec` 又把执行目录切回 `Node.cwd`。
- 普通 `Node.exec` 继续使用 `Node.cwd`。远端 `Node.scriptdir` 继续随 `Node.cwd` 变化，不改为固定目录；目录上下文结束后恢复现有目录行为。
- SSH 与 Docker 复用现有连接上传及执行能力，在 Node 层组织依赖集合和目标父目录，不新增连接层的依赖声明协议。
- 新项目模板增加内容为 `{}` 的声明文件。模板 README 说明声明维护方式、相对路径约定、远端目标复用规则，以及执行工作目录变化对相对输入、参数和输出位置的影响；复用现有模板复制和打包机制。
- 同步更新方法说明和调用示例。既有调用需要移除项目目录层级的 `scripts/` 前缀；不保留旧路径语义的兼容分支。

## Testing Decisions

- 主要测试入口为公开的 `Node.exec_script`，复用现有 Node 测试中的临时项目、DummyPipeline 与 FakeConnection。通过上传的文件及位置、目标执行工作目录、参数、环境变量、返回结果和错误观察行为，不断言内部递归函数、数据结构或固定遍历顺序。
- 辅助入口为 CLI 的项目初始化命令，复用现有 CliRunner 和临时项目测试，验证生成的声明可解析为空字典，并随模板说明一同交付。不为依赖解析新增单独的公开测试接口。
- 单脚本场景覆盖缺少声明文件、空声明、目标脚本无对应条目，以及根目录和子目录中的目标脚本。测试文件放在临时项目的脚本根目录内，并以新的相对路径参数调用，替换原来使用项目外绝对路径的测试语义。
- 依赖场景覆盖直接依赖、间接依赖、重复声明及共享依赖去重、子目录结构，以及不同子目录中的同名脚本，验证实际上传集合与目标位置。
- 远端复用场景覆盖目标首次不存在和后续已存在：首次上传完整集合，后续不上传、不重新设置目标权限，仍执行目标脚本。远端目标已存在时，即使本地声明格式错误或本地依赖缺失，也不触发依赖检查或补传。
- 目标不存在而依赖已存在时，验证依赖仍随完整集合上传，避免实现额外引入逐个依赖复用规则。
- 错误场景覆盖非法 JSON、顶层非字典、值非列表、列表元素非路径字符串、绝对路径、越界路径、项目外入口、缺少目标或依赖文件，以及直接和间接循环。断言错误说明足以定位问题，检查失败后没有文件上传和目标执行。
- 通过入口路径验证，确认本地定位与当前 Pipeline 项目目录一致；本地进程目录变化不会改变源文件来源，远端 `node.dir(...)` 只影响本次远端脚本目录。
- 执行场景覆盖脚本工作目录为 `Node.scriptdir`、参数和环境变量传递、`nixenv` 包装、结果返回及执行错误传播。普通命令的工作目录和目录上下文恢复继续由现有 Node 行为测试保护。
- SSH 与 Docker 的共同行为在 Node 层通过现有连接接口验证，连接自身的上传与执行契约沿用已有测试；如实现触及连接层，补充相应适配器行为验证。假连接测试不等同于真实远端执行验证。
- 验收时运行扩展后的 Node 与 CLI 测试，以及仓库现有测试套件。本文仅定义实施后的验证要求，生成规格本身不代表功能测试已通过。

## Out of Scope

- 自动扫描或解析脚本内容、推断 shell 引用关系。
- 新增可配置脚本根目录、目录外目标脚本支持或旧入口路径兼容分支。
- 远端目标脚本存在时修复缺失依赖、比较文件内容、自动刷新或逐个依赖判断是否上传。
- 新增仅准备不执行的接口、安装包依赖交付接口，或修改其他业务项目的打包流程。
- 重设计远端脚本目录生命周期、修改普通 `Node.exec` 的工作目录、修改 SSH 或 Docker 的依赖处理协议。
- 为网络上传失败增加事务、回滚或断点续传机制。
- 实施本规格中的代码改动、发布框架版本，或跨仓库批量迁移调用者。

## Further Notes

- 本规格依据当前设计目录已记录的逐项决定整理；先前完整方案的原文保存在 [design-notes.md](design-notes.md)，用于保留讨论依据。
- 使用根词汇表中的“脚本根目录”“目标脚本”“依赖脚本”“脚本依赖声明”。执行目录决定与现有“脚本在脚本根目录中执行”ADR 保持一致；该 ADR 当前状态为 `proposed`，本次不修改其状态。
- 本地声明缺失的兼容与入口路径的迁移是两项不同约定：前者按空声明处理，后者仍必须改用相对脚本根目录的参数。
- 脚本执行目录变化不仅影响脚本之间的引用，也影响所有相对文件输入、相对参数及输出位置。迁移时应逐一核对这些行为。
- 本地 Markdown 即本项目的工作跟踪系统。此规格使用 `ready-for-agent` 状态，不额外拆分实施任务。
