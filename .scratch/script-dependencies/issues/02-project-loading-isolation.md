# 02: 确保项目 Scripts 加载隔离并明确初始化失败

**What to build:** 同一进程切换多个项目时，各 Pipeline 始终使用自己项目的 Scripts；项目脚本接口缺失或加载失败时，在 Pipeline 初始化阶段暴露真实原因，使维护者能够直接修正项目结构或导入错误。

**Blocked by:** 01: 通过项目 Scripts 入口完成脚本执行切换。

**Status:** ready-for-agent

## Acceptance criteria

- [x] 同一进程先后实例化具有同名脚本包和同名 Scripts 类的两个项目，分别通过真实 Pipeline 阶段调用入口时，使用各自的类、入口行为、本地脚本内容和依赖声明。
- [x] 加载第二个项目后，再调用第一个项目已有实例仍使用第一个项目的实现；无需调用者清理模块缓存或手动配置搜索路径。
- [x] 项目目录使用相对路径建立后，本地工作目录变化不会使 Scripts 或脚本来源指向另一个项目；定位以当前 Pipeline 的项目目录为准。
- [x] 项目脚本包入口文件或 Scripts 类缺失时，Pipeline 初始化明确失败，不返回可继续运行的空脚本集合。
- [x] 项目类不符合 Scripts 基类或节点构造契约时，初始化明确失败；遵守契约的空 Scripts 类可以用于无脚本项目。
- [x] 项目模块中的语法错误和内部导入错误在初始化时暴露并保留可定位原因。不得将模块内部的 ModuleNotFoundError 当作项目接口不存在而静默回退。
- [x] 初始化错误与执行时校验保持分离：模块语法或导入错误不能因远端目标已存在而跳过；合法 Python 模块中的畸形 DEPS 仍只在实际调用入口且远端目标不存在时校验。
- [x] 正常加载仍只绑定当前节点，不在 Scripts 初始化时读取尚未就绪的节点脚本目录或新增脚本相关远端操作。
- [x] 通过临时项目与真实 Pipeline 验证上述行为。跨项目测试之间不手动清空脚本包缓存，不通过预置假的项目模块绕过实际加载流程，也不约束加载器内部缓存命名或导入 API。
- [x] 错误路径及多项目场景使用任务 01 的同一公开调用边界和连接替身，不为加载器私有函数增加独立测试边界；已有单项目脚本交付与执行回归继续通过。

## Scope notes

依据本功能已确认的《Scripts 项目脚本接口规格》。这是对项目加载实际行为的完善，不引入通用插件系统、可配置 Scripts 类选择或额外 Pipeline 类型注解；具体隔离实现由实现者选择。
