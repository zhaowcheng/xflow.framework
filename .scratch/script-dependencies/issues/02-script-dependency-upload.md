# 02: 按脚本依赖声明上传完整依赖集合

**What to build:** 脚本编写者维护显式脚本依赖声明后，框架在远端目标脚本不存在时递归收集本次需要的目标脚本及依赖脚本，完成全部检查后去重上传，使目标脚本能按脚本根目录中的相对路径引用直接和间接依赖。远端目标已存在时继续直接复用，不读取声明或补传依赖。

**Blocked by:** 01：统一目标脚本的路径与执行目录。

**Status:** ready-for-agent

- [x] 从本地脚本根目录读取 `deps.json`，由脚本编写者声明直接依赖，不扫描或解析脚本内容来推断依赖。
- [x] 缺少声明文件等价于空字典；空声明及目标脚本没有对应条目时，均按无依赖处理。
- [x] 声明必须为字典，键为脚本相对路径，值为依赖脚本相对路径组成的列表；非法 JSON、顶层类型错误、值非列表及非字符串路径均明确报错。
- [x] 检查整份声明的结构和路径是否合法；声明的键及列表元素禁止绝对路径和越出脚本根目录的路径。
- [x] 递归收集目标脚本的直接和间接依赖，以同一脚本相对路径匹配声明及定位本地／远端文件；重复声明和共享依赖不会导致同一次调用中重复上传同一文件。
- [x] 文件存在性及循环依赖检查仅针对本次目标脚本可达的集合；无关条目中的文件缺失或循环不阻止本次调用，也不上传无关脚本。
- [x] 上传前完成声明格式、路径范围、本次所需文件及循环检查；检查失败时不上传任何文件，也不执行目标脚本。文件缺失错误指出所缺文件，直接和间接循环错误包含循环路径。
- [x] 检查通过后，按需创建远端父目录，上传目标脚本和全部依赖脚本并保留相对目录结构；不同子目录中的同名脚本保持各自位置。
- [x] 远端目标脚本不存在时，即使部分依赖脚本已在远端存在，也按本次完整集合上传，不新增逐个依赖的存在判断、内容比较或更新规则。
- [x] 入口通过路径范围检查后，先判断远端目标是否存在。目标已存在时不读取声明、不检查本地依赖、不补传文件、不重新设置目标权限；本地声明格式错误或依赖缺失均不影响这一复用行为。
- [x] SSH 与 Docker 共用 Node 层的依赖收集及目录组织行为，复用已有连接上传和执行接口，不新增连接层依赖声明协议。
- [x] 通过公开 `Node.exec_script` 调用验证无声明、直接／间接／共享依赖、重复声明、同名脚本、首次上传、远端复用及全部错误场景；观察实际上传集合、目标位置和目标执行，不断言固定遍历顺序或内部递归结构。
- [x] 扩展后的 Node 测试及仓库现有测试套件通过；如实现触及连接层，补充对应适配器行为验证，并区分假连接测试与真实远端验证。
- [x] 不增加仅准备不执行的接口、安装包依赖交付接口或网络上传失败后的回滚机制，不修改其他业务项目的打包流程。
